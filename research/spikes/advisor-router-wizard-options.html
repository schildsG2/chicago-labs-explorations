Advisor Router Wizard — Options Report

Sep 02, 2026

1. Executive Summary

We're deciding how to build a 3-4 step wizard for the advisor router CTA on public alternatives pages, replacing the current 2-step fetch+inject flow. Five existing codebase patterns are viable models; none is a perfect fit as-is since the polished patterns are vendor-admin-only and the public-safe patterns are unpolished. Recommendation: build on Option C (Buyer Intent Audiences' Turbo Frame pattern), borrowing the StepIndicatorComponent and ModalFooterComponent from Option B (Self-Serve Events). This gets Turbo-native, accessible, auth-free step orchestration with a real progress indicator, without rebuilding the 901-LOC Stimulus wizard skeleton from scratch.

2. Options Matrix

Option Effort Polish Auth Work Extensibility Accessibility
A. Extend Current Advisor Router Low-Med Low None Low Low
B. Self-Serve Events (Turbo Streams + Stimulus) Medium High Med (rebuild public) High High
C. Buyer Intent Audiences (Turbo Frames + Hidden Fields) Low-Med Med Med (rebuild public) Med Med
D. G2 Audiences (Turbo Streams + Session Store) Low-Med Med Med (rebuild public) Med Low-Med
E. Form Stepper (Client-Side DOM Toggle) Very Low Low-Med None Low Low

Note on "Auth Work": all patterns except A and E are currently vendor-admin-gated, but in every case the orchestration pattern itself is auth-agnostic — the work is building a new public controller, not stripping auth logic out of a shared one.

3. Option Details

A. Extend Current Advisor Router — the existing 143-LOC Stimulus controller with fetch+innerHTML injection, already live on the target pages with zero auth work. Tradeoff: quality ceiling is low — manual event rebinding, no focus management, no progress indicator, gets fragile past 2-3 steps. Best for a fast MVP where polish doesn't matter.

B. Self-Serve Events Pattern — Elevate Modal + Turbo Streams atomically updating five DOM targets (header, step indicator, content, footer, hidden ID) per step, with a form object doing per-step validation. Tradeoff: production-grade polish and reusable StepIndicatorComponent/ModalFooterComponent, but it's vendor-admin-coupled and the heaviest to adapt (~450 LOC of new/adapted code). Best for a wizard you expect to keep growing and want done right the first time.

C. Buyer Intent Audiences Pattern — a single Turbo Frame that server-renders the next step partial on each submit, with state carried as hidden JSON fields. No custom Stimulus needed. Tradeoff: simplest true multi-step server-driven pattern with progressive enhancement, but ships with no step indicator, no draft save, and hidden-field state gets messy if the flow branches. Best for a clean, moderate-complexity 3-step flow.

D. G2 Audiences Pattern — same Turbo Stream/frame idea as C, but wizard state lives in a FlowSession server-side session object instead of hidden fields. Tradeoff: state survives page refresh, cleaner state encapsulation, but still vendor-coupled, no step indicator, and currently prototype-stage (mock data). Best if refresh-survival matters more than polish.

E. Form Stepper Pattern — all steps pre-rendered in the DOM, a generic 189-LOC Stimulus controller toggles visibility with client-side validation only. Tradeoff: fastest possible build, zero server round-trips between steps, but no server-side validation until final submit, no refresh survival, and all step content (including any conditional/sensitive options) ships on initial load. Best for the absolute fastest path with lightweight, non-sensitive fields.

4. Recommendation

Start with Option C (Buyer Intent Audiences pattern), enhanced with B's StepIndicatorComponent and ModalFooterComponent.

Why not the others outright:

  • A doesn't scale cleanly to 3-4 steps with the polish a lead-gen flow needs — innerHTML injection and manual rebinding is the wrong foundation to build on for extensibility.
  • B is the most polished and extensible, but committing to it means porting ~450 LOC (public controller + form object + step components + adapted Stimulus skeleton) for a first pass. That's the right target to grow into, not the right size for the first cut.
  • D adds session-store complexity (size limits, survives-refresh guarantee) the advisor router doesn't clearly need — a popover flow abandoned mid-way is fine to restart.
  • E is fastest but has the wrong tradeoffs for a lead-gen form: no server validation between steps and all steps visible in the initial DOM (inspectable) is a weak fit for a flow collecting contact info.

C fits best because: it's already a proven public-controller-shaped pattern (Turbo Frame + hidden-field state, no session dependency), matches the 3-4 step / linear flow described (contact preference → contact info → use case/company → confirmation) without needing branching logic, and is a small enough lift (~150-200 LOC total) to ship quickly. Layering in B's step indicator and footer components closes C's two biggest gaps — visible progress and consistent Previous/Next affordances — without importing B's full validation/draft-save machinery, which this flow doesn't need (no drafts, no vendor session to persist to).

This also sets up a clean upgrade path: if the flow later needs branching or draft-save, migrating from Turbo Frame + hidden fields to full Turbo Stream multi-target updates (B) is a natural next step, not a rewrite.

5. Suggested Approach

Start here:

  1. Controller shape: Model AdvisorRouter's new controller directly on BuyerIntentAudiencesController — params[:step] + params[:direction], switch on step number, turbo_stream.replace targeting a single frame (e.g. advisor_router_wizard). Keep it inheriting from ApplicationController (like the current SoftwareAdviceAdvisorRouterController), not VendorAdmin::ApplicationController.
  2. Form object: Port the shape of AudienceForm.from_params — deserialize hidden-field state each request — into a new AdvisorRouterForm covering contact preference, name/contact, use case/company.
  3. Step indicator: Reuse StepIndicatorComponent (90 LOC) as-is — takes current_step, renders circles/connectors with completed/active/pending states. Drop it into the modal header.
  4. Footer: Reuse ModalFooterComponent (54 LOC) for Previous/Next, wiring its actions to the new controller's step params instead of the Self-Serve Events Stimulus actions.
  5. Modal wrapper: Use Modal::Component (already used by Buyer Intent Audiences) rather than hand-rolling modal markup.
  6. Step partials: Write 4 step partials (contact preference, name/contact, use case/company, confirmation) following the Buyer Intent Audiences step-partial structure.
  7. Validation errors: Reuse ErrorSummaryComponent from Option B for accessible (role="alert") per-step validation feedback.

Files to reference directly:

  • BuyerIntentAudiencesController — controller/step-switch skeleton
  • AudienceForm — hidden-field state serialization pattern
  • StepIndicatorComponent, ModalFooterComponent, ErrorSummaryComponent — reuse verbatim
  • advisor_router_controller.js / AdvisorRouter::PickerComponent — current CTA trigger and modal-open logic to preserve (only the fetch+innerHTML injection gets replaced by the Turbo Frame)
  • Modal::Component — modal wrapper

6. Appendix: Software Advice Wizard Deep Dive

Supplementary research — not a competing recommendation. This section documents the lead-acquisition wizard powering softwareadvice.com's "How much will Product cost?" modal, for pattern reference against the Options B/E recommendation above.

6.1 SA Wizard UX Pattern Inventory

The SA pricing wizard (lead-acquisition-service repo, React/Next.js) is a 5-step progressive disclosure flow:

Step Question Input Type Auto-Advance?
1. Size "How many are in your organization?" Radio buttons Yes — clicking advances instantly, no button
2. Industry "What is your specialty?" Dropdown + explicit Next button No
3. Features "Select features you need" Multi-select checkboxes No
4. Contact Name, email, phone Form fields No
5. Schedule Call scheduling Calendar/time picker No

Notable UX details:

  • Auto-advance on single-select (Step 1) eliminates a click and creates momentum going into the flow.
  • A "STEP 2 OF 5" counter (FormStepCounter component) manages expectations up front.
  • Authenticated users skip contact info entirely — Step 4 auto-fills from session and can be bypassed.
  • Back is always available; forward-skipping is never allowed, which guarantees data completeness at submission.
  • Orchestration is deliberately simple: useState(formStep) + goToNextStep(), an incrementor, paired with a deepestFormStep tracker so validation errors never surface on steps the user hasn't reached yet.

6.2 SA Technical Architecture (For Reference Only)

This is React/Next.js code — zero lines are reusable in G2's Rails+Stimulus stack. The value here is pattern-only, not code:

  • LAS (lead-acquisition-service): a standalone Next.js app at lead-acquisition-service.capterra.com, embedded via iframe on SA pages. Each step is an independent React component receiving formData, goToNextStep, and setFormData as props; data accumulates in parent state via setFormData({...formData, industry: selected}). Deployed separately from the host page.
  • bx-forms (bx-monorepo): a separate package exposing a mountModalForm() widget API for non-React hosts. Internally uses a useMultiStepForm hook (step index + cumulative formData + nextStep/prevStep/reset). Bundles React 19, Nimbus v3 UI, Zod, and react-hook-form. Brand injection happens via a factory: createBrandedModalForm(brandConfig).

6.3 Could We Embed the bx-forms Widget on G2?

Factor Widget Embed (bx-forms) Native Rails+Stimulus (Recommended Options B/E)
Bundle size ~200KB+ (React 19 + Nimbus + Zod + react-hook-form) ~5KB (Stimulus controller)
Styling Nimbus v3 — foreign to Elevate Elevate-native, visually consistent
Submission pipeline Requires gateway endpoint → Eloqua Direct to G2's lead pipeline
Analytics GDM analytics SDK (not Amplitude/Ahoy) G2's existing event tracking
Customization Limited to existing props/config Full control over every step
Maintenance Tied to GDM release cadence G2 team owns fully
Time to ship Days (if gateway exists) 1-2 sprints

Verdict: don't embed. The widget bundles an entire React runtime plus a foreign design system (Nimbus, not Elevate), and its submission pipeline targets Eloqua rather than G2's lead infrastructure. The only scenario where embedding earns its keep is a throwaway POC to validate the flow concept before investing in a native build — not a production path.

6.4 Recommended Step Sequence for G2 Advisor Router

Adapting SA's flow to G2's context:

Step Question Input Type Notes
1. Contact Preference "How would you like to get advice?" Radio buttons, auto-advance Mirrors current advisor router step; keeps existing entry point
2. Company Size "How large is your team?" Radio buttons, auto-advance SA's most successful step; lowest-friction qualifier
3. Use Case "What are you looking for?" 3-5 checkboxes from category features Replaces SA's "Industry" — G2 already knows the category from the page context
4. Contact Info Name + email or phone (based on Step 1 preference) Form fields Conditional on Step 1 choice; lighter than SA's full form

SA's Step 5 (call scheduling) can be deferred to a post-submission flow. G2 should show value immediately after Step 4 — either a personalized shortlist or a confirmation ("An advisor will contact you within X hours") — rather than adding a scheduling step to the core wizard.

6.5 SA Patterns Worth Stealing

Regardless of which option (A-E) we build on, these are worth adopting directly:

  • Auto-advance on single-select steps — no "Next" button when there's only one choice to make.
  • "(Optional)" label on skippable steps — set explicitly in the step counter copy, not just implied by leaving a field blank.
  • Step counter with back button — SA's FormStepCounter shows "STEP N OF M" with a back arrow; G2's StepIndicatorComponent from Option B does the same job and should be used as-is.
  • Qualifying-questions-before-contact-info ordering — sunk-cost sequencing that reduces drop-off on the fields that matter most (name/phone/email).
  • Authenticated shortcut — SA uses useAuthUser() to skip or pre-fill contact info for logged-in users; worth replicating wherever G2 has an identified/logged-in buyer session, even in this otherwise-anonymous flow.
  • deepestFormStep tracker — don't show validation errors on steps the user hasn't reached yet; only validate steps they've actually visited. This is a small but important refinement on top of whatever step-tracking Option C's controller ends up doing — worth building in from the start rather than retrofitting.
